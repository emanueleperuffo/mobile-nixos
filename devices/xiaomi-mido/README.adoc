== Device-specific notes

This device is part of the generic https://github.com/msm8953-mainline[msm8953-mainline] port, sharing the boot stack with the other Qualcomm MSM8953/SDM450/SDM632 devices.

=== Touchscreen

mido ships with either a FocalTech FT5435 or a Goodix GT917D touch controller.
The one fitted to your unit is selected at build time via
`mobile.hardware.touchscreen` (default `"focaltech"`); the matching device tree
node is enabled in the boot image during the build.

Check which one you have once booted:

```
 $ dmesg | grep -iE "goodix|edt|ft5"
```

=== RAM

The Redmi Note 4 ships in 2GB, 3GB and 4GB variants. The device default (3GB) is intentionally set as a low-priority default so it can be overridden cleanly. If your unit has 4GB, set it in your `configuration.nix`:

```
{ config, lib, pkgs, ... }:
{
  mobile.hardware.ram = 1024 * 4;
  ...
}
```

A plain assignment is enough (no `mkForce` needed), since the default is only a `mkDefault`.

== Firmware

=== GPU (bundled)

The Adreno 506 ZAP shader firmware (`a506_zap.mdt` / `a506_zap.b02`) is bundled into the initrd automatically via `mobile.boot.stage-1.firmware`. It is sourced from the OEM firmware dump kept in https://github.com/Kiciuk/proprietary_firmware_mido[`Kiciuk/proprietary_firmware_mido`], the same source postmarketOS uses. No action is needed.

=== Modem and Wi-Fi firmware

The proprietary firmware is *not* bundled into the image. Instead, the stock
`modem` (FAT16) and `persist` (ext4) partitions are mounted read-only at boot
below `/run/mnt` (mounted by the stage-1 init, which creates the mountpoints) and
copied into `/lib/firmware` — the kernel's default firmware search path (see
`modules/quirks/qualcomm/msm8953-modem.nix`).

No manual copy is needed, but make sure those partitions exist and still
contain the stock firmware (e.g. from the stock image or a TWRP backup). The
`wcn36xx` (Wi-Fi) and `qcom_q6v5_mss` (modem) drivers are loaded only once the
firmware is in place.

== Connectivity

=== Wi-Fi

WCNSS Wi-Fi is driven by the `wcn36xx` kernel driver. The network stack is
managed by NetworkManager using the `iwd` backend:

```
 $ nmcli device wifi connect "<SSID>" password "<password>"
```

=== Cellular modem

The modem runs on `qrtr-ns` and `rmtfs` (which shares the modem's EFS/NV
region), and is managed by ModemManager through NetworkManager.

ModemManager is *opt-in*: the device/family wires up the transport (`qrtr-ns`,
`rmtfs`, the firmware copy) and shapes the ModemManager service (pulled into
normal boot, restarting until the modem appears on QRTR), but does not start
it. Activate it in your `configuration.nix`:

```
networking.modemmanager.enable = true;
```

[NOTE]
Modem support is still best-effort. `rmtfs` serves the modem's partition-backed
region with `-P`; confirm `/dev/disk/by-partlabel/` contains `modemst1`,
`modemst2`, `fsc` and `fsg`, and that ModemManager detects the modem.

=== Voice calls (`q6voiced`, opt-in)

The kernel side (QDSP6 Q6Voice modules, the `q6voicedai` device-tree node) and
userspace daemon (`pkgs.q6voiced`) are all in place, but voice calls are *not*
enabled by default: the feature is untested on mido and depends on
ModemManager's voice API. To try it, run the daemon as a service from your
`configuration.nix`:

```
{ pkgs, ... }:
{
  systemd.services.q6voiced = {
    description = "QDSP6 voice daemon";
    wantedBy = [ "multi-user.target" ];
    after = [ "ModemManager.service" "qrtr-ns.service" ];
    serviceConfig = {
      ExecStart = "${pkgs.q6voiced}/bin/q6voiced";
      Restart = "always";
      RestartSec = "2";
    };
  };
}
```

Check the actual binary name under `$out/bin/` after building, and drive calls
through ModemManager's voice API (`mmcli -m 0 --voice ...`). If this proves out
on real hardware, the service belongs in `devices/families/msm8953-mainline`
so every device in the family gets it.

=== Virtualization (KVM)

KVM is a dead end on mido — the hardware supports it (the Cortex-A53 cores have
EL2), and the msm8953-mainline kernel even ships with `CONFIG_KVM=y`, but the
firmware blocks it in a way that cannot be worked around:

- The Qualcomm https://github.com/msm8916-mainline/qhypstub[qhypstub] project
  (which makes EL2 usable on Snapdragon 410/615 by replacing the proprietary
  `hyp` firmware) https://github.com/msm8916-mainline/qhypstub/issues/10[does
  not work on MSM8953]: unlike MSM8916/MSM8939 there is *no separate `hyp`
  partition* on msm8953 — the hypervisor functionality is embedded in the
  `tz` (EL3) firmware.
- Confirmed for mido: the partition table (`partitions_64GB.gdisk`) only has
  `sbl1` and `tz` — no `hyp`. The qhypstub author's advice is to check for a
  `hyp` partition; mido does not have one (https://github.com/msm8916-mainline/qhypstub/issues/4[same
  finding for the Redmi 6 Pro]).
- Getting EL2 would require reverse-engineering and *modifying the signed TZ
  firmware* itself — a different class of project from qhypstub (and one with
  brick/EDL-recovery risk).
